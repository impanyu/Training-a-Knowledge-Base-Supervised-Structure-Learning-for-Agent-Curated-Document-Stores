# v9 — Training a Knowledge Base (T39)

New experiment, new sibling package `src/kb/` (leave `src/ca` v7 untouched).
One LLM agent "trains" a document knowledge base on QA pairs — answering
supervised questions and consolidating what it verified into the store's
structure — then an independent reader agent is examined on held-out
questions against the frozen KB. The KB is the model: learning curves,
generalization gap, per-question-class transfer.

## 1. The store

```
doc {
  id:          "d017"                     (assigned, stable)
  summary:     auto-generated, agent CANNOT set it
  statements:  [(sid, text), ...]         sid globally unique ("s0421")
  links:       [doc_id, ...]              ids only, no stored copies
}
```

- **Statements are immutable text.** Agents never author or edit sentence
  text; every statement instance descends from a build-time original via
  `origin` (copies share origin). Fabrication is impossible by construction;
  duplication = origins with >1 live instance; coverage = % of origins with
  ≥1 live instance. All integer-exact.
- **Auto-summary**: whenever a doc's statement set changes it is marked
  dirty; at iteration end every dirty doc gets its summary regenerated by a
  fixed summarizer call (configurable model, default gpt-5-mini, temp 0,
  fixed prompt, ≤60 tokens) and its embedding recomputed (chroma default
  ONNX EF over the concatenated statements — reuse the v5 embedding infra).
  Link changes do NOT trigger either. Empty doc → summary "(empty)".
  Build-time summaries are generated once with the same summarizer and
  cached in the universe file.
- `delete_doc` cascades: statement instances die with it (an origin's last
  instance dying = coverage loss, allowed), inbound link entries are removed
  from all other docs, embedding row dropped.

## 2. Actions (11, one static tool schema, tool_choice=required)

```
flow:     answer(text) · done()
sense:    search(query) -> top-k (doc_id, summary)        [k=5]
          read(doc_id)  -> statements (sid: text) + links (doc_id, live summary)
edit:     copy_statement(sid, to_doc)   new instance, same origin
          move_statement(sid, to_doc)   atomic copy+delete
          delete_statement(sid)         this instance only
          link(a, b) / unlink(a, b)
          create_doc(sids=[], link_ids=[])   both optional; sids = bulk copy
          delete_doc(doc_id)
```

Invalid ids / dead sids -> "ERROR: ..." result, recorded like any result.
No per-doc tool variation, no dynamic schema.

## 3. Short-term memory

Pinned task block + FIFO(K=30) of (action -> result) pairs, full results,
untruncated. Lifecycle: **reset at the start of every iteration (train AND
test), accumulate within the iteration across both phases, discarded at
iteration end.** No cross-question carryover anywhere. K=30 >= N1+N2, so
the in-iteration trajectory is never evicted; Phase 2 reads Phase 1's
trajectory straight from the FIFO (no injection mechanism).

Task block, train Phase 1: question, remaining budget.
Train Phase 2 adds: my answer, gold, F1 (delivered as answer()'s result).
Test: question + remaining budget only. Gold never appears in test.

## 4. Loops

**Train iteration** (per (q, gold) in train set, per epoch):

```
Phase 1  forward   budget N1=15   tools: search/read/answer
  one answer() allowed; its RESULT contains gold + F1; Phase 1 ends
  immediately on submission (leftover N1 budget is forfeited).
  Budget exhausted without answer -> auto-record F1=0, gold still revealed,
  proceed to Phase 2.

Phase 2  backprop  budget N2=15   tools: search/read + 7 edit actions + done
  agent consolidates per the three objectives (see §5); ends on done() or
  budget exhaustion. Dirty summaries/embeddings regenerate now.
```

**Test iteration** (frozen KB, per q in a test split):

```
budget M=15   tools: search/read/answer   fresh memory each question
answer(text) ends the iteration; its result is empty ("submitted").
Budget exhausted without answer -> scored 0 and counted separately as
"unanswered" (report answered-wrong and unanswered as distinct rates).
```

Multi-epoch: train set re-presented (shuffled per epoch, seeded). Test runs
against a snapshot: **epoch 0 (untrained KB = pure RAG baseline)** and after
each epoch. KB snapshots saved per epoch (docs JSON; embeddings rebuilt on
load or cached).

## 5. Agents

**Training agent** system prompt carries exactly three objectives, stated as
goals, not mechanisms (HOW to consolidate is its choice — links, hub docs,
copies, cleanup; judged only by whether a non-reasoning future reader could
answer this class of question more easily):
1. answer the question correctly;
2. consolidate the verified reasoning into the store's structure;
3. generalize the fix to the question's CLASS, not just this instance.

**Test agent** ("reader"): fresh, minimal prompt — answer the question using
search and read; submit a short answer; "unknown" if not determinable.
Never edits, never sees gold.

Both: gpt-5-mini default, temp 0.3, max 4096 tokens/turn, static schema.

## 6. Universe generator (`python -m kb.build`)

Self-contained Python generator in the PhantomWiki style (fictional persons;
zero contamination; cite PhantomWiki as inspiration; no Prolog dependency —
our question classes are Python-derivable).

- **Entities**: n_people (default 120). Family trees (2–3 generations,
  spouse links, children caps), plus Erdős–Rényi friendships. Attributes:
  job (50-word vocab), hobby (40), city (20). Names sampled to be unique,
  fictional (seeded faker-style lists).
- **Facts -> statements** via fixed templates, self-contained, no pronouns:
  "Alice Johnson's job is arborist." / "Alice Johnson is married to Bob
  Meza." / "Carol Meza is a child of Bob Meza." Each fact renders into the
  subject's doc (relations render one statement per endpoint doc:
  Alice's doc gets the marriage statement, Bob's doc gets the mirrored one —
  two distinct origins, intentionally).
- **Initial store**: one doc per person, statements in, **zero links**.
- **Question classes** (template ids recorded on every question):
  - QC1 single-hop attribute: "What is the job of X?"
  - QC2 2-hop: "What is the job of X's spouse?" (relation × attribute grid)
  - QC3 3-hop: "What is the hobby of the father of X's spouse?"
  - QC4 aggregation: "How many children does X have?" (children/friends/
    grandchildren; numeric gold as digits AND word accepted via grader
    normalization — store gold variants)
  - QC5 unanswerable: well-formed question whose relation chain is empty in
    this universe ("What is the job of X's brother?" where X has no
    brother). Gold = "unknown".
  Every question stores: template id, hop count, gold (+variants), and the
  support set (origin sids needed) for post-hoc diagnostics.
- **Splits** (seeded, disjoint). Two levels: 5 CATEGORIES (QC1–5), each
  containing several concrete TEMPLATES (e.g. 2-hop = spouse→job,
  father→hobby, friend→city, ...; ~12–15 templates total).
  - `train` (150): i.i.d. over ALL five categories, drawn from most
    templates of each — train distribution = task distribution, like normal
    ML. Never exclude a whole category.
  - `test_in` (100): unseen instances of TRAINED templates — the primary
    generalization measure.
  - `test_out` (50): 1–2 RESERVED templates per category, never used in
    train (category seen, template unseen) — within-category transfer.
  Instance-level disjointness everywhere.
- Output: `data/v9/universe.json` (docs incl. cached summaries, fact graph,
  questions, splits, vocab). Deterministic per seed.

## 7. Grading

SQuAD-style normalize/EM/F1 (copy the 32-line grader from ca). Multi-gold
via variants list. Unanswerable questions: correct iff normalized answer is
"unknown" (plus a small accepted-alias list); report their accuracy
separately, never blended into headline F1.

## 8. Recording & report

- `trace.jsonl`: every action of every iteration (run kind, epoch, qid,
  phase, step, action, input, result, tokens).
- `train_log.jsonl`: per train iteration — qid, template, F1, steps used,
  answered-at-step, phase-2 action counts by type.
- `test_log.jsonl`: per test question — split, qid, template, F1, EM,
  steps, answered|unanswered|wrong.
- `kb_stats.jsonl`: per epoch — docs, live statements, distinct origins
  alive (coverage), duplicate origins, links, orphan docs (no in/out links),
  created docs, deleted docs.
- `python -m kb.report <run_dir>`: learning curve table (test F1 by epoch ×
  split, incl. epoch-0 RAG baseline), per-template-class breakdown,
  generalization gap (train-forward F1 vs test_in F1), edit-type mix,
  KB stats trajectory. Plain JSON + printed table; no plotting.

## 9. CLIs

```
python -m kb.build --seed 0 --people 120 --out data/v9
python -m kb.train --universe data/v9/universe.json --epochs 2 --seed 0
                   --model gpt-5-mini --out runs/kbv9_e2
                   [--train-size N] [--n1 15] [--n2 15]
python -m kb.test  --kb <snapshot.json|universe.json> --split test_in|test_out|both
                   --out ... [--m 15] [--limit N]
python -m kb.report <run_dir>
```

kb.train runs the epoch-0 test itself? No — keep orthogonal: train only
trains and snapshots; kb.test evaluates any snapshot. A convenience
`--eval-each-epoch` flag on kb.train may invoke the test loop on both splits
with a --limit.

## 10. Tests (offline only — stub LLM policy, stub summarizer, hash EF)

- store mechanics: copy/move/delete semantics + origin bookkeeping; link/
  unlink; create_doc variants (empty / sids / links); delete_doc cascade
  (instances die, inbound links cleaned, coverage drop recorded); dirty
  marking + batch regeneration at iteration end only; summaries never
  agent-settable.
- sids/doc ids: global uniqueness, dead-id errors.
- memory: task block pinning per phase; FIFO reset per iteration, retained
  across phase transition, K eviction.
- loops: single-answer enforcement; answer result carries gold+F1 in train
  and nothing in test; budget enforcement per phase; forfeiture of leftover
  N1; auto-F1=0 on exhausted Phase 1; done() ends Phase 2; unanswered
  accounting in test.
- generator: determinism per seed; split disjointness; spot-check gold for
  each question class incl. an unanswerable and an aggregation case; support
  sets reference real origins.
- grader: ports of the existing tests + variants + unknown handling.
- e2e: scripted mini universe (8 people), scripted policies driving one full
  train epoch + test pass; report computation on the artifacts.

## 11. Experiment plan (what the report must serve)

- **E1 learning curve (headline)**: test_in / test_out F1 vs epoch (0..3);
  epoch 0 = untrained store = baseline B1. Later: baselines B3 GraphRAG /
  B4 RAPTOR / B5 HippoRAG 2 as horizontal lines (separate task, external
  implementations adapted to the same corpus; NOT in this task's scope).
- **E2 baseline table**: method × {test_in, test_out} × {F1, one-time build
  tokens, per-question tokens}. kb.report must emit build/query token
  tallies so the table is assemblable.
- **E3 generalization anatomy (free, log slicing)**: train-forward (valid
  from epoch 2) vs test_in vs test_out; per-category and per-template
  breakdown.
- **E5 structure analysis (free, trace mining)**: edit-type mix per epoch,
  link-graph vs fact-graph alignment (share of built links connecting docs
  that co-occur in some question's support set), emergent hub docs (created
  docs by in/out degree), KB stats trajectory.

Datasets: KBGym is this task. Official-PhantomWiki and MuSiQue adapters are
follow-up tasks (statement unit = paragraph for MuSiQue; category = official
composition shape; test_out = held-out shape).
